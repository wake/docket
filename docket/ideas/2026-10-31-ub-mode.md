---
title: What Docket could take from ub-mode and its tools
---

Recorded 2026-10-31. The maintainer asked what Docket could borrow from
[ub-mode](https://github.com/unclebob/ub-mode), and asked for it to be kept
as an idea. The notes below come from reading its README and SKILL.md and the
READMEs of its tools; none of the tools has been run yet, and nothing below
is decided.

## What it is

ub-mode is one SKILL.md: short rules for writing code, in three parts (make
it work, make it right, practice), paired with four tools by the same
author:

- **crapper**: a CRAP score per function, `CC² × (1 − coverage)³ + CC`,
  so a function that is both complex and untested scores high. It writes
  `.metrics/crap.edn`; `--changed` limits it to git additions and edits,
  and `--threshold` fails the run above a score.
- **dryer**: candidate duplicates, scored by the similarity of their
  normalized structure. It writes `.metrics/dry.edn`.
- **mutator**: mutation testing. `--changed` limits it to git additions and
  edits; later runs rerun only the survivors and the functions whose text
  changed; it exits 3 when a mutant survives. Each worker mutates a private
  copy of the file. It writes `.metrics/mutate/<namespace>.edn`.
- **uml-viewer**: draws components from a policy and per-language parsers,
  colors them by the CRAP and mutation snapshots, and marks in red a
  dependency that points from a higher level to a lower one.

The first three read Clojure, Java, Go, TypeScript, Rust and Python.
uml-viewer's parsers read Clojure, TypeScript, Rust and Python, not Go. The
tools are Python programs that create a `.venv` and install packages on
their first run. The ub-mode repository has no license, so its ideas can be
used but its text is not copied.

## Leads

- **Choosing what to baseline.** A baseline written by an agent for one
  small package (174 lines) came to about 18 words of proposal and spec per
  line of code, so a whole existing codebase cannot be baselined at once. Per-function and
  per-package metrics could pick the parts: high CRAP marks complex,
  untested code that most needs a spec; a high mutation score marks code
  whose tests already pin its behavior and can stand as a spec's evidence;
  duplicate candidates are worth merging before they are specified twice.
  ub-mode's rule "do one unit by hand, then build the tool that matches it"
  fits: one package is done by hand first, and the tool must give the same
  map.
- **Snapshots as optional input.** The tools write stable files keyed by
  namespace and function name, which a viewer joins. `dkt` produces facts
  that need no language parser; it could read such snapshots when they are
  present, and never require them. The workbench could show them the same
  way.
- **The changed-lines mutation check.** The workflow template asks that
  mutating the changed lines makes a test fail. Today the mutants are
  written by hand for each task. mutator's `--changed` with its reruns could
  do this for Go. It would be named in the user's workflow file, not shipped
  as a dependency of Docket.
- **Rules worth wording into the workflow template or review prompts:**
  - a test that would still pass if every function returned nothing tests
    nothing, which sharpens the "tests got weaker" focus of a test-only
    review;
  - when two fixes that rest on one premise fail the same check, the
    premise is written in one sentence before a third fix is tried, which
    is close to the fix loop's breaker;
  - one rule per line, in the imperative, is shorter than Docket's prose.

## Not to take

- "Push to the main line at the end" conflicts with Docket's pull request
  merged with a merge commit.
- Hard thresholds over a whole existing codebase (CRAP under 10, every
  duplicate removed) would start large restructurings on adoption. Applied
  to changed code only, or as a ratchet that may not get worse, they fit
  better.
- Coding discipline itself (TDD, domain modeling) stays with superpowers
  and the agent; Docket keeps to triage, paths and bookkeeping.

## Open questions

- Whether the tools' Go support holds up on this repository: crapper's
  complexity and coverage, mutator's operators, whether `--changed` covers
  changed lines or whole changed functions, and how long a run takes.
- Whether `dkt` should read `.metrics/` snapshots at all, or leave them to
  the agent and the workbench.
- Whether the workflow template should name an outside tool, or describe
  the check and leave the tool to the user's workflow file.
- Which of the rules above belong in the shipped workflow template rather
  than in one user's workflow file.
