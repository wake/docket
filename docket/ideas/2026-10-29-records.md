---
title: Records for fixes, restructurings, tests and prompts
---

Recorded 2026-10-29. The points below were decided with the maintainer; the
change that takes this idea turns them into a proposal and deltas.

## Problem

Work on the light review path (a fix that restores specified or existing
behavior, a restructuring, tests for existing behavior, prompt text) opens
no change, so nothing in the repository says what was done, why, how it was
checked and what the review found, and `dkt status` cannot list it.

## Decided

- One record per piece of work: `docket/records/<slug>.md`, with YAML front
  matter `title`, `kind` and `source`.
- Kinds: `fix` restores a known answer (a specified or existing behavior, or
  a wrong test); `refactor` changes no behavior (moving code and
  restructuring tests included); `test` adds tests for existing behavior;
  `prompt` is text agents act on, for any purpose. Work that sets a new
  expectation always opens a change.
- `fix` leaves the kinds of `dkt new` in the same change, so the word means
  one thing: a bug whose right behavior cannot be stated is a
  `change-request`. No archived change used the `fix` kind.
- `dkt record <slug> --kind fix|refactor|test|prompt --title "..." --source "..."`
  writes the file from the kind's template, and refuses a slug a change or
  another record already uses.
- Commits carry `Record: <slug>` in the final paragraph, like `Change:`.
- A record can hold tasks in the plan's format (`### Task N: <name>` with
  `- [ ]` steps); their commits add `Task: N`, `dkt sync` ticks them, and
  `dkt status` shows progress. `dkt lint` checks them with the plan's task
  rules, without requiring `**Scenarios:**` or `**Review:**`. Tasks add no
  review.
- Sections: every kind has title, source and review (what the review found
  and how it was handled). `fix`: symptom, cause, fix, regression test.
  `refactor`: motivation, scope, evidence that behavior did not change.
  `test`: behavior tested, mutation check result. `prompt`: motivation,
  reach (which copies, whether it ships), mechanical check result.
- `dkt lint` checks the front matter and the kind, that every section is
  filled with no template text left, and that a fix's regression test file
  exists.
- A record is done when it merges into the default branch; it is not
  archived. The scan finds records in progress on worktrees and branches the
  way it finds changes, and `dkt status` reports them, with when they merged
  and the first tag that holds them.
- A record never grows into a change: the triage decides the path, and a
  large record splits into pull requests by the usual rules.

## Open questions

- How records appear in `status --json`: in the list of changes with a
  field telling them apart, or in a list of their own.

## Status

`add-records` made records exist: `dkt record`, the template, lint, the
skill text. It settled some points differently from Decided: slugs carry the
date and take a `-2` suffix instead of being refused; a fifth kind,
`checks`; one template with four shared sections, each limited to 60 words,
instead of sections per kind. Tracking remains for a second change: the scan
reads records, `dkt sync` ticks their tasks, `dkt status` lists them, and
`Record:` trailers are read.
