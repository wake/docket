title: Issues, apart from ideas
---

Recorded 2026-11-01. The points under Decided were decided with the
maintainer.

## Problem

All pending work in this repository is written as an idea. About half of
the fifty ideas are fixes, optimizations and tests found during development,
work whose expected behavior is already settled. The order mixes them with
work that needs design, which `2026-10-29-ideas-and-order.md` lists as an
open question on classifying ideas.

## Decided

- Ideas and issues are separate.
  - An idea is work that needs design and changes a spec; it is queued in
    `docket/order.md` and becomes a change.
  - An issue is a request or a piece of work whose expected behavior is
    already settled, such as a fix that restores specified behavior, an
    optimization or a test, done on the light review or direct merge path
    with a record. Requests from other people come in as issues too.
- Issues do not depend on GitHub Issues. A project can keep them in its
  forge's tracker (GitHub, Gitea) or, as the fallback, as files at the level
  of the ideas, for example `docket/issues/<date>-<slug>.md`.
- Docket ships a base issue template that fits the spec. An issue has the
  same structure whether it lives in GitHub, in Gitea or in a file.

## From research, 2026-11-01

Notes, not decided:

- Open-source processes take an issue first and ask for a design proposal
  only for substantial work. PEP 1: "Most enhancements and bug fixes don't
  need a PEP and can be submitted directly to the Python issue tracker."
  Rust RFCs, Go proposals, Kubernetes KEPs and Swift Evolution draw the
  same line, and a proposal keeps a tracking issue.
- SDD tools: spec-kit has a `bug` extension that skips the feature workflow
  and takes an issue URL. Kiro's bugfix spec lists the current behavior,
  the expected behavior and the behavior that must not change.
- A common split for a bug: the code departs from the spec (an issue, the
  spec stays); the spec misses the case or is wrong (an idea or a change).
  Docket's triage already draws this line between light and full review.

## Open questions

- The template's sections. Candidates: what happens, what is expected, what
  must not change, where it was found, the source.
- How a project says which tracker it uses, given that Docket links to no
  outside system on its own (`dkt` would read only issue files; a forge's
  issues would go through the forge's CLI at the user's request).
- How an issue found to change a spec moves to an idea or a change, with
  `--source` naming the issue.
- Whether `dkt lint` checks issue files, and how a record names its issue.
- Where the template lives for each forge (GitHub reads
  `.github/ISSUE_TEMPLATE/`; Gitea's location is to be checked).
- Moving the existing ideas that are issues once the format exists.

## Status

Done by the change `add-issues`: the issue template, `dkt issue`, lint of
file issues and of the sources that name them, `dkt status` listing file
issues with their derived state, and the `docket` skill's rules. The tool a
project uses is named in its `AGENTS.md` (`## Issues`), not in the user's
workflow file. Moving the ideas of this repository that are issues is left
to a piece of work of its own.
