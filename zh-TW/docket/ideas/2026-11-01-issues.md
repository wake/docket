2026-11-01 記錄。「已決定」之下的各點已與維護者定案。

## 問題

這個 repository 中所有待辦的工作都寫成 idea。五十個 idea 中約有一半是開發時發現的修正、最佳化與測試，也就是預期行為已經確定的工作。order 把它們與需要設計的工作混在一起，這就是 `2026-10-29-ideas-and-order.md` 列為 idea 分類之待釐清問題的事。

## 已決定

- idea 與 issue 分開。
  - idea 是需要設計且會改 spec 的工作；它排進 `docket/order.md` 並成為 change。
  - issue 是預期行為已經確定的請求或工作，例如還原已規定行為的修正、最佳化或測試，走輕審或直接合併路徑並搭配 record 完成。來自其他人的請求也以 issue 進來。
- issue 不依賴 GitHub Issues。專案可以把它們放在 forge 的追蹤器（GitHub、Gitea），或作為後備，放成與 idea 同一層的檔案，例如 `docket/issues/<date>-<slug>.md`。
- Docket 隨附符合 spec 的基本 issue 範本。不論 issue 放在 GitHub、Gitea 或檔案，結構都相同。

## 來自研究，2026-11-01

筆記，非定案：

- 開源專案的流程是先開 issue，只有大型工作才要求設計提案。PEP 1：「大多數的增強與 bug 修正不需要 PEP，可以直接提交到 Python 的 issue 追蹤器。」Rust RFC、Go proposal、Kubernetes KEP 與 Swift Evolution 劃的是同一條線，而提案會保留一個追蹤 issue。
- SDD 工具：spec-kit 有一個 `bug` 擴充，跳過功能流程並接受 issue URL。Kiro 的 bugfix spec 列出目前的行為、預期的行為，以及必須維持不變的行為。
- bug 常見的切分：程式碼偏離 spec（issue，spec 不動）；spec 漏了這個情況或有錯（idea 或 change）。Docket 的分流已經在輕審與全審之間劃了這條線。

## 待釐清問題

- 範本的各節。候選：發生了什麼、預期什麼、什麼必須不變、在哪裡發現、source。
- 專案如何說明它用哪個追蹤器，因為 Docket 自己不連結任何外部系統（`dkt` 只會讀 issue 檔案；forge 的 issue 則依使用者要求透過 forge 的 CLI）。
- 被發現會改 spec 的 issue，如何移成 idea 或 change，用 `--source` 指名該 issue。
- `dkt lint` 是否檢查 issue 檔案，以及 record 如何指名它的 issue。
- 每個 forge 的範本放在哪裡（GitHub 讀
  `.github/ISSUE_TEMPLATE/`；Gitea 的位置待確認）。
- 格式存在之後，搬移屬於 issue 的既有 idea。
