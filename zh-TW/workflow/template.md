# Docket workflow steps

`docket` skill 分流出的每條路徑所要做的審查與驗證步驟。
其餘的由 skill 負責：分流、change 資料夾、plan 的格式、commit trailer 與合併。

## Full review

1. 在寫任何程式碼之前，連同 proposal、delta spec 與 design.md 一起審查 plan 一次
   （見 Reviews），並修正審查發現的問題。
2. 逐 task 執行 plan，每個 task 用一個新的實作者 agent，先寫測試。
   每位實作者拿到它的 task 的 Reuse 列，並回報它新增的每個匯出符號，
   以及為什麼沒有任何既有的符合需求。
   結構調整與行為改變分開 commit。
3. 只有標 `**Review:** judgment` 的 task 有自己的審查者，在新的 context 中。
   每個改程式碼的 task 改為接受機械檢查：
   親眼看到它新增的測試在程式碼之前失敗、之後通過，
   而對它改動的行做突變會讓某個測試失敗。
   不改程式碼的 task，例如只編輯文件的，由它自己的驗證步驟檢查。
4. 合併之前，整個 change 審查一次，由兩位審查者平行進行：
   一位用不同的模型，受命攻擊（錯誤結果、邊界情況、部分失敗、程式碼其他地方的同一個缺陷），
   另一位在新的 context 中，對照 proposal 與 delta spec 檢查程式碼
   （沒有其他模型可用時見 Reviews）。修正之後，只有大的修正才再審一次。
5. 只有在以下情況才拆 PR：混了不相干的關注點、結構重構與行為混在一起
   （重構先走，放在自己的 PR）、或產品程式碼加測試遠超過約 1000 行。
   不要用 stacked PR。

## Light review

1. 依編輯的種類驗證：
   - 修正：寫回歸測試，並看到它在修正之前失敗；
   - 重構：涵蓋該程式碼的測試在改動前後都通過，
     而對改動的行做突變會讓其中一個失敗；沒有任何一個失敗時，先以只改測試的編輯補上測試；
   - prompt 文字：用機械方式檢查，不用找字串的測試：
     它仍能載入，而且每份副本說的一致；
   - 測試：對它們涵蓋的程式碼做突變；測試必須失敗；
   - 檢查設定：執行它們；PR 自己的 CI 執行會用新的設定，
     審查要看有沒有檢查變弱了。
2. 合併之前，讓整個 diff 被審查一次（見 Reviews）。

## Check

合併之前，讓一個新的 agent 只拿 diff 和分流的定義，確認每一個改動的行都是註解或空白，
而且沒有任何註解會改變程式碼的建置或執行方式。
如果它不能確認，重新分流。

## Direct merge

只執行讀取該編輯所改內容的檢查：只改沒有東西會建置、內嵌或測試的文件時，一個都不跑；
改程式碼、測試檔或依賴清單時，跑建置與測試。不審查。

## Reviews

必要的審查由不同模型的審查者進行。沒有的話，由新 context 中的同一個模型進行。
如果也做不到，PR 要註明它沒有獨立審查，並請人來審查。作者自己的閱讀不算審查。
